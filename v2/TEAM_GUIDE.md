# v2 팀 안내 — 익산 악취 민원 예측 재설계

> 이 문서는 PR 리뷰와 운영 인수인계를 위한 안내서다. v2의 출력은 **실제 악취 농도·발생원 판정이 아니라, 다음 30분 추가 민원 접수 위험의 Top 3 우선순위**다. 특정 농가를 원인으로 단정하거나 행정조치를 자동으로 수행하지 않는다.

## 1. 한눈에 보는 변경점

| 항목 | 기존 기본 코드 | v2 |
|---|---|---|
| 예측 단위 | 1km 격자 Top 3 | 동일 |
| Event | 공통 Event 160개를 시간순 70/30으로 한 번 분할 | 신고가 몰리는 순간 발동하는 `trigger k=7`을 주 운영 Event로 사용 |
| 입력·라벨 | 초기 민원과 다음 30분 민원 | 입력 30분, 다음 30분 라벨을 명시적으로 분리 |
| Event 선정 | 기존 방식의 기준과 평가가 한 파이프라인에 섞여 있음 | 선정은 예측시점 이전 정보만 사용; 예측창 민원은 라벨에만 사용 |
| 검증 | 단일 시간순 70/30, 평가 가능 Event 47개 | expanding-window rolling-origin, 주 운영 테스트 Event 합 102개 |

| 외부 데이터 | 기상은 운영 참고정보 | AWS 분 단위 기상·농가 좌표를 수집. 아직 정식 학습 변수에는 넣지 않음 |

## 2. Event란 무엇인가

`Event`는 민원이 늘어난 순간에 담당자가 “다음 30분 어디를 먼저 확인할까?”를 묻는 한 번의 예측 업무 단위다.

```text
T-30분                     T                         T+30분
|------ 입력: 이미 접수된 민원 ------|------ 라벨: 이후 추가 민원 ------|
                                       ↑
                                  예측·현장 판단 시점
```

### 주 운영: trigger k=7

- 최근 30분 안에서 서로 다른 30m 위치의 민원이 **7곳째** 들어온 분이 끝나는 즉시 발동한다.
- 그 다음 분을 예측 시점 `T`로 삼는다.
- 발동 뒤 60분은 다시 발동하지 않아, 앞 Event의 미래 라벨이 다음 Event 입력에 들어가지 않게 한다.
- `k=7`은 성능을 보고 고른 값이 아니라, 테스트 Event 합이 100개 이상인 값 중 가장 큰 값이라는 사전 규칙으로 선택했다.(평가 가능한 Event 수를 확보하면서도 발동 기준을 최대한 엄격하게 유지하기 위해 사전에 정한 규칙으로 선택)

### 보조 검증: session k=4

- 민원이 60분 이상 조용하다가 새로 들어온 첫 신고를 시작점으로 한다.
- 보수적이지만 Event 수가 적으므로, 주 운영을 대체하지 않고 결과 강건성 확인에 사용한다.

## 3. 평가 구조

| 원칙 | v2 구현 |
|---|---|
| 미래 차단 | 모든 입력 변수는 `T` 이전만 사용. 다음 30분 민원은 라벨 전용 |
| 시간 검증 | 2019~2020 학습→2021 테스트, 2019~2021→2022처럼 학습기간을 확장 |
| 최근 기간 | 2023년 이후는 반기 단위 폴드. 표본이 작은 폴드는 ‘참고용’ 표기 |
| 기본 비교 | prior만 / 초기 민원 수 상위 3 / 무작위 |
| 신뢰구간 | Event 단위 paired bootstrap 95% CI. prior 대비 개선 구간이 0을 포함하면 채택하지 않음 |
| 운영 한계 | 입력 신고 주변 후보 반경 밖에서 발생한 실제 민원은 모델이 맞힐 수 없으므로 후보 밖 비율을 모든 결과와 함께 본다 |

`Hit@3(전체)`은 후보 밖 정답도 실패로 세는 실제 운영 관점 지표다. `Hit@3(후보내)`는 이미 후보 안에 들어온 정답만 대상으로 후보 간 순위를 잘 올렸는지 보는 조건부 지표다.

## 4. 코드 지도

```text
v2/
├─ data.py              민원 로드, 1km 격자, 시간·공간 조회 인덱스
├─ events.py            trigger/session Event 생성과 라벨·후보 격자
├─ features.py          기존 15개 + 과거 민원 이력 변수
├─ folds.py              rolling-origin expanding-window 폴드
├─ experiments.py        비교할 기준선·모델 묶음 목록
├─ run_v2.py             학습, 평가, 결과표 생성의 시작점
├─ evaluation.py         prior 대비 paired bootstrap 신뢰구간
├─ evaluate_step2.py     핫스팟·중복 신고·시기 변화 추가 진단
├─ tests/                Event·누수·평가 회귀 테스트
└─ data_ext/             농가 지오코딩·AWS 기상 수집·외부 데이터 산출물
```

VS Code에서는 프로젝트 루트를 열고 `v2/run_v2.py`를 기준 진입점으로 보면 된다. 주 운영 재현 명령은 아래와 같다.

```powershell
cd v2
..\.venv\Scripts\python.exe run_v2.py --mode trigger --k 7
```

Windows에서 가상환경 경로가 다른 경우에는 팀원의 Python 환경에서 `requirements.txt`를 설치한 뒤 `python run_v2.py --mode trigger --k 7`을 실행한다. API 키가 필요한 외부 수집은 `v2/.env`에만 두며 Git에 올리지 않는다.

| AWS 관측소 | `v2/data_ext/stations.csv` | API 조회 결과 | 익산 중심 20km 이내 5개 관측소 |

| 축산농가 좌표 | `v2/data_ext/farms_geocoded.csv` | **2024-12-31 기준 농가 현황** | 현재 운영 참고지도 전용 |

### 농가 데이터의 사용 원칙

농가 좌표 1,267곳 중 1,265곳을 지오코딩했다. 그러나 단일 기준일(2024-12-31) 자료이므로 2019~2024 과거 Event 학습 변수에는 사용하지 않는다. 과거 농가 허가·등록·사육두수 이력을 확보하기 전에는 다음 용도로만 쓴다.

```text
누수 없는 민원·기상 모델 → Top 3 위험 격자
                              ↓
                 현재 농가 지도·축종·규모를 현장 점검 참고로 표시
```

따라서 화면 문구도 ‘발생원’이나 ‘원인 농가’가 아니라 **‘주변 현장 점검 참고 농가’**로 표기한다.

## 6. 외부 데이터 처리 상태

### 기상

- 변수 후보: 풍향·풍속·기온·습도·강수의 최근 15/30/60분 요약과 변화량.
- 결측은 값만 채우지 않고 `weather_available`, 관측소 거리, 결측률을 함께 변수화한다.
- 풍향은 0°와 360°가 연결되므로 단순 평균 대신 `sin/cos` 또는 원형평균을 사용한다.
- 기상은 Event 안의 모든 후보에 공통일 수 있으므로, 최종적으로는 민원 확산 변수 또는 풍향×발생원 공간 변수와의 상호작용을 평가한다.

### 농가×풍향

과거 농가 이력이 확보된 뒤에만 정식 모델 실험으로 승격한다. 후보 격자별 상류 1/3/5km 농가 수, 축종별 두수, 거리 감쇠 규모, 풍향 일치도와 최근 15/30/60분 누적 노출지수를 만든다.

## 8. 운영자가 받는 결과

담당자에게는 모델 점수 자체보다 다음을 제공한다.

1. 다음 30분 현장 확인 우선 격자 Top 3
2. 신뢰도와 후보 밖·기상 결측 경고
3. 최근 민원 확산, 시간대, 기상 상태 등 점수 근거
4. 현재 농가 현황을 겹친 현장 점검 참고지도

이 결과는 담당자의 출동·점검 우선순위를 돕는 도구이며, 특정 농가의 위법·배출 사실을 판정하는 증거가 아니다.
